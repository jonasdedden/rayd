# Design: Rust Stack

Concrete crate choices for the v1 implementation. Pinned versions reflect what's stable in early 2026; verify and lock at project start.

## Why these and not the alternatives

### `pyo3` over `rust-cpython`
`rust-cpython` is effectively legacy; PyO3 is the de facto standard. PyO3 0.23.x is mature, has structured exception support, async bridge, buffer protocol access, and the proc-macro ergonomics needed for `pyo3-stub-gen`.

### `tokio` over `glommio` / `smol`
`glommio` is Linux-only and io_uring-based; we run on macOS and on container environments without io_uring. `smol`'s ecosystem is thinner; `tonic` and most production crates assume tokio. Multi-thread tokio gives work-stealing across CPU cores for free.

### `tonic` over `grpc-rs` / `volo-grpc`
`grpc-rs` wraps the C++ gRPC library and has a painful build. `volo-grpc` is CloudWeGo's framework — strong Thrift, weaker gRPC ecosystem outside ByteDance. `tonic` is pure Rust on `hyper`, integrates with `tracing`, supports rustls and native-tls, and has full bidi streaming for the owner pub-sub channels.

### `memmap2` + `nix` over `shared_memory`
`shared_memory` is a higher-level wrapper but its locking primitives (`raw_sync`) are minimal and the abstraction leaks on Windows. We need exact control over `mmap` flags (`MAP_POPULATE`, optionally `MAP_HUGETLB`) and over `SCM_RIGHTS` ancillary data on `sendmsg(2)`. `memmap2` for the mapping, `nix` for the syscalls.

### `bumpalo` (initially) over a custom slab
For v1, plasma stores immutable objects with relatively coarse-grained allocations. A bump allocator per arena segment is enough; we recycle entire segments when their objects all drop. Once we measure fragmentation in production, we evolve. **Don't pick `talc` / `buddy_system_allocator` initially** — they're more complex than needed and don't handle our "free wholesale" pattern naturally.

### `arrow-rs` over `arrow2`
`arrow2` is in maintenance mode; its author recommends `arrow-rs` for new projects. Apache Arrow Rust ships fast and has the IPC + Flight components we need.

### Pickle via PyO3 over `serde-pickle`
`serde-pickle` cannot reconstruct arbitrary Python class instances, run `__reduce__`, or handle out-of-band protocol-5 buffers. It's only useful when payloads are known-simple. Production Ray uses CPython's `_pickle` via Cython; we use it via PyO3.

### `thiserror` + custom Python exceptions over generic `RuntimeError`
We want `try: ... except rayd.WorkerCrashed as e: e.worker_id` to work. That requires registered Python exception classes with typed fields, achieved via `#[pyclass(extends=PyException)]`. `thiserror` gives us the matching Rust enum.

members = [
    "crates/rayd-core",
    "crates/rayd-plasma",
    "crates/rayd-gcs",
    "crates/rayd-raylet",
    "crates/rayd-py",

## Stub generation pipeline

1. Each PyO3 binding file (`crates/rayd-py/src/*.rs`) annotates types and functions with `#[gen_stub_pyfunction]` / `#[gen_stub_pyclass]` alongside the regular PyO3 macros.
2. `crates/rayd-py/src/stub_gen.rs` is a small `bin` target that calls `define_stub_info_gatherer!` and writes `python/rayd/_native.pyi`.
3. `make stubs` runs `cargo run --bin stub_gen --release` and copies the output.
4. CI runs `make stubs` then checks `git diff` is empty (drift detection) **and** runs `python -m mypy.stubtest rayd._native` to enforce stub ↔ extension parity.

## Distribution

- Wheels per Python minor version (3.10, 3.11, 3.12, 3.13).
- Platforms: `manylinux_2_28_x86_64`, `manylinux_2_28_aarch64`, `macosx_11_0_arm64`, `macosx_10_15_x86_64`, `win_amd64`.
- Built in `quay.io/pypa/manylinux_2_28_*` containers via `maturin-action`.
- Source dist (`sdist`) included for from-source installs.

## Honest gaps

- `pyo3-stub-gen` is a community project; expect to file issues and possibly contribute upstream.
- `tokio-eventfd` exists but is sparsely maintained — we'll roll our own `AsyncFd`-wrapped `eventfd` (about 50 lines).
- No production-grade off-the-shelf SHM allocator in Rust matches Plasma; budget time to build and `loom`-test ours.
- Free-threaded CPython support in PyO3 is improving but not yet ergonomic; v1 ships GIL-bound, future versions can revisit.
- `arrow2` is dead — ignore tutorials that recommend it.
